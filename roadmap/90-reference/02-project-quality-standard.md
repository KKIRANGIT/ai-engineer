# Project Quality Standard

Back to [Roadmap Index](../README.md)

## Why This Reference Matters

Many learners overcount weak projects as strong portfolio evidence.

This reference defines what should count as a serious project inside this roadmap. The purpose is not perfection. The purpose is credibility.

## Minimum Standard

A project should meet most of these before you treat it as a serious artifact:

- clear problem statement
- narrow target user
- readable code structure
- working setup instructions
- deployed or demoable output
- basic monitoring or debug visibility where appropriate
- README with screenshots
- explanation of tradeoffs

If a project lacks most of these, it is better described as practice rather than portfolio proof.

## Core Quality Dimensions

Judge a project across five dimensions:

### 1. Problem clarity

Can a reader tell:

- what the project does
- who it helps
- what workflow it improves

### 2. Technical clarity

Can a reviewer understand:

- the architecture
- key files or modules
- how to run it
- what major design decisions were made

### 3. Usability

Can a user:

- understand the main flow
- recover from common mistakes
- tell what state the system is in

### 4. Reliability

Does the system handle:

- invalid input
- basic errors
- missing data
- failure states

### 5. Proof quality

Does the project leave behind:

- repo
- README
- screenshots
- demo path
- explanation of limitations

## Minimum README Standard

A strong README should usually contain:

- project name
- one-sentence summary
- problem statement
- target user or use case
- stack used
- local setup
- screenshots or demo media
- architecture summary
- known limitations
- next improvements

## Minimum Standard For AI Projects

AI projects should meet the normal project standard plus:

- prompt or tool logic documented
- known failure cases listed
- some evaluation approach
- grounding or validation where correctness matters

## AI-Specific Quality Questions

For AI projects, ask:

- is the output merely plausible, or is it grounded
- can structured output be validated
- can failures be categorized
- is the user shown enough evidence or uncertainty
- can the system be evaluated consistently

## Milestone Project Standard

A milestone project should usually include:

- clearer project scope
- stronger documentation
- visible tradeoff discussion
- at least some operational thinking
- better polish than weekly practice artifacts

## What Does Not Count As Strong Proof

Examples of weaker evidence:

- tutorial clones with minimal adaptation
- generic chatbots with no specific user problem
- repos with no README or screenshots
- projects that only work on one machine with unclear setup
- demos with no clear explanation of architecture or behavior

## Expert Notes

### A finished small project beats an ambitious broken one

Finishability is a real skill signal.

### Documentation quality changes perceived technical quality

Poorly presented work is often undervalued, even when the code is decent.

### AI projects need stronger honesty

It is better to document limitations clearly than to imply false reliability.
