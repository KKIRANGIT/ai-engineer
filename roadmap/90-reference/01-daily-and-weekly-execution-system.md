# Daily and Weekly Execution System

Back to [Roadmap Index](../README.md)

## Why This Reference Matters

Roadmaps fail less from lack of information and more from lack of execution structure.

This reference exists to give you a stable operating rhythm for the whole preparation journey. It is meant to reduce drift, prevent passive learning, and make progress visible.

## Core Principle

Consistency is more valuable than occasional intensity.

The purpose of your execution system is to make sure that:

- learning becomes implementation quickly
- implementation becomes proof
- proof becomes reviewable
- review becomes the input to the next cycle

## Daily Minimum

On a constrained day, your minimum viable day should still include:

- `30-60 min` learning
- `60-90 min` building
- `10-15 min` writing notes or logging progress

This is enough to preserve continuity and avoid losing momentum.

## Ideal Deep-Work Day

An ideal deep-work day usually includes:

- one focused concept block
- one implementation block
- one debugging or refactor block
- one short publishing or review block

Good pattern:

- learn one concept from docs or notes
- build the main feature or exercise
- debug and refactor what broke
- document what changed in your understanding

## Recommended Weekly Split

Use this as a default unless a project deadline demands otherwise:

- `20-30%` learning and docs
- `50-60%` implementation
- `10-15%` debugging and cleanup
- `10-15%` review, documentation, and publishing

If your week becomes mostly content consumption, the loop is off balance.

## The Weekly Execution Loop

Every week in the roadmap should roughly follow this loop:

1. Understand the week’s real objective.
2. Study the minimum theory needed to start.
3. Build the main artifact.
4. Debug and tighten weak areas.
5. Write what you learned.
6. Review whether you actually met the exit criteria.

This is the loop that converts a roadmap from "interesting reading" into skill growth.

## Daily Operating Questions

At the start of the day, ask:

- what is the one concrete thing I need to ship today
- what concept is blocking that
- what is the smallest visible proof I can produce before stopping

At the end of the day, ask:

- what moved forward
- what got stuck
- what should I do first tomorrow

## Weekly Review Questions

Use these every week:

- what did I ship
- what did I understand poorly
- what took too long
- what failed repeatedly
- what did I avoid because it felt confusing
- what is the next bottleneck to fix

## Weekly Review Template

Keep a weekly review note with:

- week number
- hours spent
- topics covered
- artifact shipped
- biggest technical challenge
- biggest process failure
- what improved
- next week's first task

## Anti-Drift Rules

These rules keep the roadmap from becoming shallow:

- do not start a new week without shipping the current week’s main artifact
- do not count passive watching as progress
- do not open too many side projects
- do not skip the review loop because you are "busy"

## Execution Modes

### Recovery mode

Use this when you are overloaded or losing momentum.

Goal:

- protect continuity

Do:

- one small coding task
- one short note
- one visible commit

### Standard mode

Use this for most weeks.

Goal:

- hit the full weekly deliverable

### Intensive mode

Use this when you have unusual time or are near a milestone.

Goal:

- finish a concentrated build cycle

## Expert Notes

### Output beats intention

Your progress should be observable from files, repos, notes, demos, or cases.

### Review is part of execution

Without review, repeated mistakes stay invisible.

### Bottleneck awareness compounds

The fastest learners often improve because they fix the process bottleneck, not only the topic gap.
