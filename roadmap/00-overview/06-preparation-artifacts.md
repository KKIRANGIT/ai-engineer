# Preparation Artifacts

Back to [Roadmap Index](../README.md)

## Why Artifacts Matter

Learning without artifacts is hard to review, hard to present, and hard to monetize.

Artifacts serve three purposes at once:

- they make your own thinking clearer
- they create external proof
- they reduce future work because you can reuse structure and language

This file defines the minimum artifact system you should maintain across the full roadmap.

## Artifact Categories

You should maintain artifacts in five categories:

- identity artifacts
- execution artifacts
- project artifacts
- AI-specific artifacts
- market-facing artifacts

## 1. Identity Artifacts

These define how your work is seen from the outside.

### GitHub profile

Your GitHub profile should communicate:

- what you are building
- what your strongest projects are
- what technologies you can actually use
- evidence of consistency

Minimum standard:

- pinned repositories
- useful profile README
- clean repo naming
- visible commit activity over time

### Portfolio site or portfolio README

This should not be a vanity page. It should be a proof index.

For each serious project include:

- project name
- one-sentence problem statement
- stack
- screenshots
- demo link
- repo link
- short architecture or tradeoff summary

## 2. Execution Artifacts

These keep the roadmap operational.

### Learning journal

Keep a running journal in Markdown, Notion, or another structured format.

Record:

- what you learned
- what confused you
- what broke
- what fixed it
- what patterns repeated

This becomes valuable for:

- self-review
- interview storytelling
- content writing
- portfolio explanations

### Issue tracker

Track your roadmap work as if it were a real product backlog.

Create issues for:

- weekly deliverables
- project features
- bugs
- refactors
- research tasks

This helps you practice scoped delivery and prevents fuzzy goals from piling up.

### Reusable project template

Maintain a starter template for your common app pattern.

Typical contents:

- base folder structure
- linting and formatting
- env handling
- test setup
- deployment notes
- common README structure

The template reduces friction and increases your shipping speed over time.

## 3. Project Artifacts

Every serious project should leave a structured trail.

### Project brief

Create a short project brief before building:

- problem
- target user
- desired workflow improvement
- scope boundaries
- success metric

This prevents building vague demos with no real evaluation target.

### Architecture note

For each serious project, record:

- system components
- data flow
- model provider choices
- retrieval or tool boundaries
- deployment shape
- monitoring and failure surfaces

It does not need to be long. It needs to be clear.

### README

Your README should do more than explain setup.

A strong project README includes:

- what the project does
- why it exists
- stack used
- local setup
- screenshots
- architecture summary
- tradeoffs
- limitations

### Case study

A case study is the bridge between code and credibility.

Good structure:

- problem
- why existing workflow was weak
- what you built
- key technical decisions
- challenges and failures
- results or expected impact
- what you would improve next

## 4. AI-Specific Artifacts

These are especially important for AI-focused work.

### Prompt library

Maintain a reusable prompt library.

Organize prompts by:

- extraction
- classification
- summarization
- reasoning workflows
- tool use
- safety or refusal behavior

Do not just store prompts. Store notes on:

- what each prompt is for
- where it fails
- what variants you tested

### Eval set

Every serious AI project should have some form of evaluation set.

This can be simple:

- representative inputs
- expected properties of outputs
- pass/fail or rubric-based scoring

Without this, improvement claims stay weak.

### Failure log

Track recurring failure patterns:

- retrieval misses
- hallucinations
- schema failures
- latency spikes
- unsafe tool suggestions
- confusing UX states

This log sharpens your engineering judgment quickly.

### Cost note

Track rough economics for each AI project:

- request cost
- cost per active user estimate
- expensive workflow steps
- optimization ideas

This is a major differentiator in interviews and client work because many builders ignore it.

## 5. Market-Facing Artifacts

These turn preparation into opportunities.

### Resume bullets

As you finish projects, write resume-ready bullets immediately.

Good bullets describe:

- what you built
- what technical challenge you solved
- what result or capability improved

### Demo script

Create a short walkthrough for each serious project.

You should be able to explain in:

- 30 seconds
- 3 minutes
- 10 minutes

### Proposal or scoping template

If you want freelance opportunities, prepare:

- discovery questions
- scope assumptions
- delivery phases
- risk notes
- pricing logic

## Minimum Artifact System

If you want the lightest acceptable system, maintain at least:

- GitHub profile
- portfolio index
- weekly learning journal
- reusable project template
- prompt and eval library
- one case study per major project

## Minimum Artifact Standard For Every Major Project

Every serious project should end with:

- problem statement
- target user
- architecture note
- stack decisions
- feature list
- tradeoffs
- screenshots
- demo URL
- repo URL
- known limitations
- next improvements

## Final Principle

Your artifacts are not documentation overhead. They are part of the preparation itself.

They make you:

- easier to evaluate
- easier to trust
- easier to hire
- easier to remember
