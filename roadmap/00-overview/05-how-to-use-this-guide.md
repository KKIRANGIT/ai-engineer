# How To Use This Guide

Back to [Roadmap Index](../README.md)

## What This Roadmap Is

This roadmap is not a book to finish. It is an execution system.

Its value comes from:

- sequence
- repetition
- shipping pressure
- reflection
- proof accumulation

If you read it passively, it will feel inspiring and produce little.

If you treat it as an operating system for a year of work, it can change your level dramatically.

## The Operating Rules

These rules are non-negotiable if you want the roadmap to work.

### Rule 1: Do not advance on familiarity

You do not move forward because a topic looks easy or familiar.

You move forward when you have:

- implemented the key idea
- shipped the week’s output
- documented what you learned

Recognition is not competence.

### Rule 2: Build before you feel ready

Many learners wait until they "understand everything."

That never happens first. Understanding follows contact with implementation and debugging.

Use the cycle:

- learn enough to start
- build quickly
- hit friction
- resolve friction
- summarize what changed in your understanding

### Rule 3: Keep public proof

If your work is invisible, it has limited market value.

Public proof means:

- GitHub repos
- READMEs
- screenshots
- demos
- architecture notes
- case studies

You do not need to publish every experiment. You do need to publish every meaningful milestone.

### Rule 4: Prefer finished work over more ideas

One finished, explainable project beats five half-finished experiments.

The roadmap rewards:

- finishability
- clarity
- reuse of prior learning

### Rule 5: Review every week

Without review, you will repeat the same weaknesses.

At the end of each week, answer:

- what did I ship
- what slowed me down
- what did I misunderstand
- what should I systematize for next week

## Recommended Study Modes

Choose one mode honestly and stay consistent.

### Intensive

- `30-40 hrs/week`

Best for:

- students
- career transition periods
- focused full-time preparation

### Standard

- `15-20 hrs/week`

Best for:

- working professionals with disciplined evenings and weekends

### Slow but serious

- `8-12 hrs/week`

Best for:

- long-term learners who still intend to finish the roadmap properly

Important rule:

- if you are part-time, stretch the calendar
- do not lower the project standard

## The Weekly Execution Loop

Every week should follow the same structure.

### Step 1: Learn the concept

Read official docs and a small number of high-quality references.

Goal:

- understand the problem space
- understand the main abstractions
- understand the common failure modes

### Step 2: Build something concrete

Apply the concept immediately.

Goal:

- expose false understanding quickly
- create code that forces precision

### Step 3: Document your understanding

Write what changed in your mental model.

Goal:

- convert messy experience into reusable understanding

### Step 4: Publish proof

Package the work so another person can inspect it.

Goal:

- create visible evidence
- make future opportunities easier

### Step 5: Review and adjust

Decide what bottleneck to remove next.

Goal:

- keep compounding instead of drifting

## Recommended Weekly Time Split

Use this as a starting point:

- `25%` concepts and docs
- `55%` implementation
- `10%` debugging and cleanup
- `10%` writing, publishing, and review

If you find yourself spending more than half your time only consuming content, the loop is broken.

## How To Read A Weekly Section

Each weekly folder should be read in this order:

1. Goal
2. Learn
3. Build
4. Deliverables
5. Exit criteria

Interpret them like this:

- Goal tells you what capability the week is trying to produce.
- Learn tells you what to study, not what to memorize.
- Build tells you where the real understanding comes from.
- Deliverables tell you what visible output should exist.
- Exit criteria tell you whether you are genuinely ready to move on.

## How To Avoid Common Roadmap Failure Modes

### Failure mode: staying too long in research mode

Fix:

- start building sooner
- limit source count
- define a small output before reading deeply

### Failure mode: rushing through weeks for completion satisfaction

Fix:

- hold the line on deliverables
- use exit criteria honestly

### Failure mode: making the roadmap too theoretical

Fix:

- convert concepts into tools, scripts, UI, workflows, or deployment artifacts immediately

### Failure mode: too many parallel projects

Fix:

- keep one main milestone project active
- allow only small supporting experiments beside it

## What To Track Every Week

Maintain a simple weekly log containing:

- hours spent
- concepts learned
- features shipped
- bugs resolved
- docs or notes written
- repo or demo links
- biggest blocker
- next-week focus

This will help you later in:

- resume writing
- portfolio storytelling
- interview answers
- self-review

## Minimum Acceptable Standard For Any Week

Even on a constrained week, try to produce:

- one implementation artifact
- one written note
- one commit trail you can point to

Consistency beats intensity spikes followed by silence.

## Pre-Start Checklist

Before starting Phase 1, make sure you have:

- Git and GitHub configured
- Python installed and virtual environment workflow working
- Node.js LTS installed
- one code editor configured well
- one SQL client available
- one HTTP client available
- Vercel, Supabase, OpenAI, and Anthropic accounts created
- a place for weekly notes
- a place for project case studies

## Final Usage Principle

Treat the roadmap as a contract with your future self:

- every phase should leave durable evidence
- every week should remove a real skill gap
- every project should raise your market credibility
